# Independent code, UX, and product review

Source revision: `843377a`. Review date: October 4, 2026.

Three independent reviewers inspected code, UX, and product coverage without
editing files or running builds. The primary developer checked their findings
against the source and the connected Samsung SM-X800 on Android 16. This review
separates reproduced defects, verified source behavior, and design proposals.

The main concern is that the catalog is growing faster than the experience for
choosing a useful sample, maintaining an experiment, and recording its results.
The actual provider widgets and pinned library identities are useful foundations.
Adding more entries does not resolve the following problems.

## Immediate defects

### 1. Comparison state changes with the layout width

Priority: P1. Reproduced on the physical device.

`CompareScreen.kt:80` creates separate SamplePanel calls inside its wide Row and
compact Column branches. `SamplePanel.kt:57` owns each sample's saved state.
The branches have different composition ancestry and saved-state keys.

The left Button count was 1 in the original wide layout. Temporarily setting
the display size to 1752 x 1000 produced a 1000-pixel-wide compact window at
340 dpi, and its left count became 0. Two real taps made that count 2. Restoring
the display size brought back the old wide count 1. The right count stayed 0.
This is a divergent experiment, not successful state preservation.

Local evidence: `.local/review-before-resize.xml`, `.local/review-narrow.xml`,
`.local/review-narrow-two.xml`, and `.local/review-wide-final.xml`. The display
override was reset after each check. Existing same-width recreation tests do
not cover this behavior.

Fix: Own the two sample states above the responsive branches, with explicit
panel identities. Add a regression that changes both panel values, crosses the
600 dp layout boundary, changes a value again, and crosses back.

### 2. Working library samples initially open as unsupported

Priority: P1. Reproduced on the physical device.

`navigation/ComponentoryApp.kt:104` initializes the detail provider to Classic.
Opening a catalog row at line 193 does not check whether that provider supplies
the component. The newly implemented badged icon opened with an unsupported
Classic sample even though both library implementations were available.
The provider menu does not show availability before a choice.

Local evidence: `.local/review-detail.png` and `.local/review-detail.xml`.

Fix: Preserve the current provider when supported; otherwise choose a supported
provider when entering a component. Mark available and unsupported choices in
the menu. Keep unsupported choices accessible for deliberate inspection.

### 3. Controls are missing accessible names

Priority: P2. Verified in the device accessibility tree and source.

The global Enabled switch in `compare/CompareScreen.kt:65` has an adjacent label
with no association. In `.local/review-compare.xml`, the switch has empty text
and content description and is marked `NAF="true"`. The detail screen repeats
this pattern. Material 2 and 3 checkbox, switch, and radio samples also put
labels beside controls without providing their names to the control semantics.

Fix: Give global controls localized accessible names or use a labelled toggle
row. Give library samples meaningful names while retaining their actual provider
appearance. Test the names of both radio choices and the Enabled switch.

## Product and UX problems

### 4. The selector implies an Android OS version switch

Priority: P1. Verified wording and placement; user misunderstanding is a risk.

`lab/DesignFamily.kt:17` prominently says `Android 1.0 · Classic`, while the
sample runs on Android 16. A modern framework Switch can appear under this
selection because availability correctly depends on the running OS. The detail
explanation is below the entire panel at `catalog/ComponentDetailScreen.kt:73`.
The documentation explains the distinction more clearly than the main control.

Fix: Use provider names such as Classic framework theme, Holo framework theme,
and Compose Material 3. Show the running Android version beside the selector.
Keep theme introduction dates as secondary information, and show exact library
versions without requiring a trip to Settings. Historical execution remains a
separate, explicitly unverified mode until an actual historical OS run exists.

### 5. The sample is too low in the information hierarchy

Priority: P2. Observed on the physical tablet; layout changes are proposals.

The List screenshot shows three complete entries on the large landscape tablet.
Compare repeats the component name in its picker and heading, followed by global
controls, panel titles, provider controls, and origin text before the sample.
Icon samples add another picker and a long source identifier above the preview.
On compact windows, whole metadata-heavy panels stack vertically.

Evidence: `.local/review-current.png` and `.local/review-compare.png`.
The resized compact captures demonstrate an unusually short window, not a
representative phone portrait screenshot.

Fix: Reduce list row padding and add provider availability. Merge the component
heading and selector. Put the live samples near the top; put detailed API/source
metadata in an expandable implementation section. Use a compact A/B comparison
layout that minimizes the distance between the two samples.

### 6. Compare does not carry the experiment made in detail

Priority: P2. Verified source behavior; not directly exercised in this review.

`navigation/ComponentoryApp.kt:143` copies the component and provider into Compare,
but the new SamplePanel creates a separate SampleState. User-entered text, range
values, counts, and icon choices are not transferred. Changing provider also
creates a fresh state because the provider is a saved-state key.

Fix: Define a simple experiment configuration that can seed each provider sample.
Make a current-state comparison copy the detail configuration, and provide an
explicit reset. A provider change should preserve compatible input or clearly
communicate why it resets.

### 7. Pending components are invisible inside the app

Priority: P2. Verified source behavior.

`catalog/ComponentListScreen.kt:47` searches only implemented LabComponent entries.
The inventory has 239 source APIs, with 90 implemented and 149 pending. A search
for a pending DatePicker or Toolbar returns ordinary no-results feedback.
Users cannot distinguish planned work from unavailable APIs or a search mistake.

Fix: Add an optional coverage view or Ready/Planned filter using the audited
inventory. Planned entries should identify their provider and lack of a runnable
sample. They must not be presented as unsupported or as original captures.

## Code and verification priorities

### 8. Catalog loading performs avoidable synchronous work

Priority: P2. Verified implementation; no timing measurement was taken.

`icons/IconCatalog.kt:83` reflects and tries to load every framework drawable
on every catalog request. Selecting an icon calls this through selected(), while
the picker has separately requested the same catalog. The initial Material
catalog parses 11,385 entries synchronously from a composable call.

Fix: Cache framework metadata by relevant resource configuration, index entries
by ID, and load initial catalogs outside composition. Measure initial load and
selection time before claiming a performance improvement. The picker also needs
selected-card treatment and a search/filter reset; those are UX improvements.

### 9. Evidence needs a stable run identity

Priority: P2. Verified limitations; not a claim that passing tests failed.

`scripts/test-device.ps1:90` overwrites `.local/device-tests.txt`. Revision, APK
hashes, environment, and exact test scope are maintained manually in documents.
The runner restores its English app-language override in finish(), which cannot
guarantee recovery after a killed or crashed instrumentation process.

The progress test uses animator scale 1.0 after zero-scale instrumentation
stalled on this device. This is a recorded test condition, not proof of production
responsiveness with animations disabled. API 24 is supported by the build, but
the different pre-33 locale implementation has not run on an older device.

Fix: Save each execution in a timestamped directory with a JSON manifest recording
revision and dirty state, APK hashes, device/build/display/language configuration,
provider versions, selected tests, changed settings, and results. Restore app
locale from the host script as well. Add explicit phone, larger-font, minimum-API,
software-keyboard, and animation-disabled scenarios as resources permit.

Support metadata and provider rendering also have separate dispatch rules.
Unhandled categories fall through to action helpers that throw. Add a catalog-wide
smoke test for declared supported combinations before extending the catalog much
further; no registry framework is necessary.

## Repair order

1. Preserve comparison state across layout changes and add the failing regression.
2. Choose supported defaults and clarify theme, library, and OS identities.
3. Move live samples up and give controls accessible names.
4. Transfer current experiment state into comparison and expose planned coverage.
5. Cache catalog loading and give verification runs stable provenance.
6. Resume component groups while retaining these checks.

Keep each repair in a focused commit after formatting, lint, and relevant tests.
This review does not change the broad component-coverage goal or claim it complete.
